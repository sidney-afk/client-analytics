# Entry tax — before/after, 2026-09-24

**Session:** Beacon · **Follows:** `2026-09-23-speed-map.md`, "Cross-cutting".
**Change:** the `<head>` boot script (`src/index/005-head-boot.html.part`) now starts the
boot `key-verify` POST and ONE batched `syncview_runtime_flags` read while the document
is still parsing, instead of after it.

## What changed, and what did not

- **Six boot flag reads are now one.** The speed map named "two" because two finished
  before content; a staff boot actually fired six separate reads of the same table
  (calendar upsert, Kasper urgent ping, write-UI reroute + client-comment gateway,
  settings, sample review). One `key=in.(...)` read replaces them. Each consumer takes
  its row once; every later read (focus, click time, realtime, heal) is live exactly as
  before, and a failed batch makes each consumer fall back to its own read.
- **Not batched on purpose:** `prod_authority` (writes must read it live before every
  intent) and `pto_v1` (the leave feature's source is pinned by
  `test/leave-evidence-fingerprint-coupling.js`; changing it means a human re-review of
  the leave screenshots). Both are follow-ups, not oversights.
- **The staff gate is unchanged.** `init()` still awaits the server's `key-verify`
  answer before any staff data is requested. What moved is *when the question is
  asked*: at the top of the document instead of after 1.4 MB of parsing. The early
  answer is accepted only once, only for boot verification, only for the exact key and
  member it was sent for, and only while under a minute old
  (`test/boot-entry-tax.js`). A forged or wrong identity is still refused by the
  server and still sees the gate.
- **Tabs do not render data before verification.** The request asked to let tabs paint
  before `key-verify` "where it is only a paint hint". The only paint-hint part is
  already painted early (the predicted tab shell, via `data-boot-nav`). Everything
  after it reads anon-readable staff datasets, which the 2026-09-10 review rule forbids
  loading before verification. Starting verification earlier gets most of the same
  benefit without loosening that rule.
- **SMM weekly reports** routes out of the head script before the staff branch, so it
  gains nothing (−61 ms is noise).

## Measurement

Same rig for both columns: this repo's `index.html` served locally, Playwright
Chromium 1440×950, warm reload, a stored staff identity, and a mocked backend with
fixed latencies (key-verify 800 ms, flag reads 350 ms, other Supabase 400 ms, other
hosts 300 ms). "First content" = the moment the tab is mounted with a verified staff
identity (`_syncviewStaffIdentityValid() && currentNav === <tab>`), i.e. the end of the
entry tax. It is **not** the live data-rendered time from the speed map: the mocked
backend returns empty data, and this sandbox has no staff key for the live site. The
