# Client-link Edge Function source review — 2026-09-26

Source-only review of `client-review-link` and `client-token-verify` on `main@3f5bd46e6086`. These are proposals, not a function change or a live-service finding. The issuer's staff check, active-client check, and never-rotate token write remain required. The browser sends `strict: true` and requires the current token; the legacy non-strict contract is separate. These boundaries are documented in [`STATE_OF_THINGS`](../STATE_OF_THINGS.md) and [`SUPABASE`](../truth/SUPABASE.md).

## Findings and proposed checks

1. **Malformed request bodies do not get one clear client error.** Both handlers turn JSON parse failures into `{}` and then cast without checking the value ([issuer lines 105–107](../../supabase/functions/client-review-link/index.ts#L105), [verifier lines 102–106](../../supabase/functions/client-token-verify/index.ts#L102)). A JSON `null` reaches property access and the generic catch, producing 500 ([issuer lines 141–145](../../supabase/functions/client-review-link/index.ts#L141), [verifier lines 160–163](../../supabase/functions/client-token-verify/index.ts#L160)). In the verifier, malformed JSON instead becomes a missing, non-strict request and can return 200 while the global mode is permissive ([lines 115–124](../../supabase/functions/client-token-verify/index.ts#L115)). Also, a present non-boolean `strict` value such as the string `"true"` is treated as false, so an invalid token can take the non-strict permissive branch ([lines 106 and 140–145](../../supabase/functions/client-token-verify/index.ts#L106)). **Proposal:** reject malformed/non-object JSON and present non-boolean `strict` with a stable 400 response before database work. Keep omitted `strict` compatible with legacy callers and keep correctly typed strict requests fail-closed. Test malformed syntax, `null`, arrays, and non-boolean `strict` in an offline handler harness; the known browser caller sends a boolean ([browser line 2163](../../src/index/260-production-refresh-boot.js.part#L2163)).

2. **Verifier dependency failures have ambiguous outcomes.** `authMode()` ignores the query's `error` and maps a missing/failed flag read to `permissive` ([lines 64–71](../../supabase/functions/client-token-verify/index.ts#L64)). `logAttempt()` awaits the event insert but never checks its returned `error` ([lines 74–91](../../supabase/functions/client-token-verify/index.ts#L74)); a rejected promise reaches the generic 500 catch ([lines 160–163](../../supabase/functions/client-token-verify/index.ts#L160)). Thus a resolved event-write error can be silent while a transport rejection can turn a valid check into 500. Strict token proof still depends on the joined client/token read and cannot pass from the flag fallback alone ([lines 127–145](../../supabase/functions/client-token-verify/index.ts#L127)). **Proposal:** define and test one explicit policy for flag-read and audit-write failures, with both returned errors and thrown failures covered. Preserve strict proof and decide legacy non-strict outage behavior with the existing F87 owner, rather than silently changing the global enforcement mode.

3. **Strict denials use different JSON envelopes.** Unsupported view returns `ok`, `valid`, `mode`, and `reason` ([lines 110–112](../../supabase/functions/client-token-verify/index.ts#L110)); missing slug adds `view` but still omits `strict`, `protocol`, and `error` ([lines 115–124](../../supabase/functions/client-token-verify/index.ts#L115)); a bad token reaches the full response shape ([lines 147–159](../../supabase/functions/client-token-verify/index.ts#L147)). All are 410 for strict requests, and the browser currently classifies any non-5xx denial as an invalid link before reading the body ([browser lines 2165–2167](../../src/index/260-production-refresh-boot.js.part#L2165)). **Proposal:** use one non-enumerating strict-denial envelope for all three paths, retain 410, and test its exact fields without exposing which credential check failed.

Existing offline coverage protects the real authority boundary: [`b0-auth-scaffold-source.js`](../../test/b0-auth-scaffold-source.js) pins strict token proof and the joined read, [`client-entry-preflight.js`](../../test/client-entry-preflight.js) exercises the browser with mocked verifier responses, and [`client-review-link-security.js`](../../test/client-review-link-security.js) plus [`client-access-provisioning.js`](../../test/client-access-provisioning.js) protect staff-only issuance and no rotation. They do not execute the malformed-body or audit-failure handler paths above. F87 already records missing request controls, uniform denials, and audit-outage behavior in [`docs/truth/SUPABASE.md`](../truth/SUPABASE.md); this report supplies source locations for that existing work. No live request, function edit, deploy, or auth-mode change was made.
