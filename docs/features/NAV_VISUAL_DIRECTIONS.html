First — a correction worth knowing

The control you like isn't actually a sliding pill. Nothing in SyncView slides today.

finding

What ships today — cross-fade

.workload-pills button.active just swaps background to white with transition: all 0.12s. There is no indicator element and no transform anywhere — the "glide" is two adjacent buttons cross-fading over a shared track. It reads as motion because they sit inside one bordered, rounded container.

What a real sliding pill looks like

One absolutely-positioned pill that translateXes to the selected button and animates its width, 340ms on an ease-out curve. Click both to feel the difference.

So this is good news: the thing you already like is the cheap version. Building a genuine sliding pill is an upgrade you haven't seen yet — and it's the smallest piece of every direction below. All three mockups use the real thing.

Gains

  • Exactly the aesthetic you like — and a real one, applied to what you look at all day.
  • Cheapest by far. CSS plus a small pill-positioning helper. No route changes, no new URLs, no gating changes, no relearning.
  • Lowest risk against PR #931 — touches one CSS block and one markup region.
  • Reversible in a single commit.

Costs

  • It doesn't fix the actual problem. Nine segments is well past what a segmented control is for (2–5). It's a prettier version of the same flat list.
  • Still no hierarchy, and still scrolls on a laptop.
  • The pill fights the scroll strip: when .header-nav scrolls, the pill must track scrollLeft or it visually detaches — the one real engineering wrinkle.
  • Tests pin .header-nav-btn { flex: 0 0 auto; white-space: nowrap } and the exact navHome < navProd < navLinear order, so the restyle must keep both.

Gains

  • Creates the missing hierarchy: daily work sits above occasional work.
  • Room to grow — a new surface joins a group instead of becoming a 10th top-level button.

Costs

  • The grouping is a judgement call — if you disagree with the buckets it's worse than flat. This is the main thing to react to.
  • Breaks a load-bearing selector. Nesting buttons inside groups breaks #headerNav > .header-nav-btn, which the active-tab scroll-into-view and three test suites depend on.
  • The route table is duplicated in a pre-paint <head> script plus hard-coded #navX CSS selectors (52 data-boot-nav references). Groups must be taught to both copies or the pre-JS highlight silently breaks.
  • Costs ~44px of vertical space on data-dense views.

Gains

  • Highest collision risk with PR #931, and the same boot-script/test rework as B.

Recommendation — B, in two shipments. Ship A first as its own PR: the real sliding pill plus the label fix. It's ~2 days, independently valuable, and it's the entire visual payoff. Who sees what — as verified in the shipping code

Surprise: the nav buttons are not role-gated at all. Every signed-in staff member — Admin, SMM or Creative — sees the same nine buttons. Access is enforced downstream: the route bounces to Analytics (Linear mirror), or the data fetch fails a capability check (Workload), or the edit controls quietly disappear. There are only three real auth roles (admin, smm, creative) — "Kasper" is a comment-author role and a ?Kasper=1 session unlock, not an auth role; "editor"/"designer" are display labels for Creative. Client-link visitors don't get a filtered nav — the whole header is removed.
Design consequence: "Respect capability" (toggle above) is a genuine improvement B and C unlock — a Creative would stop seeing four tabs that bounce or fail for them. It's also a behaviour change, not just styling: it needs your sign-off separately from the layout question.
