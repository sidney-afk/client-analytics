# Native preinstallation public-database backup preparation

This separate adapter supports an explicitly reviewed 67-table public schema. It does not widen the fixed 86/90-table complete-application formats. The original September 13 preparation had no live capture, upload or operational recovery key. Its historical PostgreSQL 17 receipts are populated synthetic `390c6f261f91431284a1a0e144576fed` and observed-schema `a00008a48e20449bb8c6301478dcbd76`, eight checks each, both servers stopped; their [manifest](../independence/LINEAR_EXIT_NATIVE_PREINSTALL_BACKUP_PG17_20260913.json) retains those original source pins. The subsequent online-mode source has separate [September 14 proofs](../independence/LINEAR_EXIT_NATIVE_ONLINE_SEQUENCE_PG17_20260914.json), including default strict behavior. Current real-capture and custody status belongs in `LINEAR_EXIT_REVIEW_REPAIRS_20260913.md`; do not infer it from either isolated fixture. The observed fixture matches the captured 67-table/115-function public catalog, but its platform prerequisites are isolated and it contains no hosted rows.

`scripts/linear-exit-native-preinstall-backup.js` exports async `capture(options)` and `restore(options)`. Supply an absolute `pgBin`, explicit `connection` (`host`, `port`, `user`, `password`, `database`, `sslmode`), and explicit existing custody inputs (`hmacInput`, distinct 32-byte `encryptionKey`, 32-character hexadecimal `keyId`). No environment credential fallback is used. Non-loopback capture requires `verify-full` TLS and the operator's configured trusted PostgreSQL CA certificate.

For capture, additionally supply `expectedCatalogSha256` from the independently reviewed full public catalog, a `sourceIdentity` label, and a new absolute encrypted `target` directory. The identity label is operator supplied, not proof that database and Storage credentials belong to the same project. A persistent read-only repeatable-read transaction exports the snapshot imported by native `pg_dump`. The custom archive retains public schema/data, owners, grants and sequence state. The encrypted manifest binds its actual SHA-256, catalog digest, row multiset fingerprints and sequence observations. Sequence observations before and after capture detect changes but do not create an atomic sequence fence.

For restore, supply the encrypted `packageDirectory`, a new absolute `outputDirectory`, an absolute `localDataDirectory` for the caller-owned running PostgreSQL cluster, and a literal loopback connection. Before creating a database, the adapter verifies the server address/port and data directory, and matches its system identifier to local `pg_controldata`; a loopback tunnel alone is insufficient. The adapter creates a uniquely named database, never restores into an existing database, and retains that database for inspection. It uses `pg_restore --single-transaction --exit-on-error`, then restores the supported publication and explicit owner-only ACL metadata in a separate scratch transaction and compares catalog, rows and sequence state. The archive bytes remain unchanged. Exactly one verified public-schema creation TOC entry is omitted so the standard empty public schema retains its PostgreSQL initial privileges. The supported publication is `supabase_realtime` with explicit public-table membership, operation flags and no column/filter expressions; unsupported forms refuse. The sole ACL correction recreates an authenticated explicit postgres-owner-only table ACL that native dumping collapses to its implicit default. No comparison is normalized or relaxed. A failure between the archive and metadata transactions can leave a partially restored private scratch database; successful return requires the final complete comparison. Failed scratch databases remain local for diagnosis; no automatic database deletion occurs. The temporary decrypted directory is removed on success or failure.

The default scratch template is `template0`. Actual Supabase public definitions can depend on platform schemas, extensions and roles. For those, provide an explicitly prepared local `scratchTemplate` with those prerequisites and no public relations. The adapter checks that public is empty before cloning. This does not independently prove that the prerequisite platform is equivalent to hosted Supabase; the final public catalog comparison must still pass.

Coverage excludes non-public publication membership, non-public schemas/data, cluster roles/passwords, Supabase Auth/platform configuration, Storage bytes and external assets. Capture those separately where required. Existing Storage inventory/export modules provide encrypted current-object bytes and metadata; they require fresh capability checks and refuse unsupported version history. Database and Storage captures are not one atomic snapshot. Plaintext scratch exists locally, so use a private encrypted disk with adequate free space. The final package is encrypted; Windows directory modes alone are not an ACL guarantee.

The user is the sole keyholder. Owner-selected storage is iOS Notes; the owner confirmed saving the complete recovery record and opening it on their phone. Keep both independent secrets and `keyId` together, separate from the encrypted backup. Do not require another password manager or another keyholder. After an authorized capture and successful scratch restore, upload only the encrypted package to the user's private Drive, retrieve it to a fresh local directory, and reopen it using that separate recovery record. No Drive automation is installed by this component.

The opt-in `native-preinstall-backup` PostgreSQL test uses only a synthetic 67-table source and fixed test keys. An isolated pass is not live backup, off-device custody or full-platform recovery proof.

## Reproduce locally

From the repository, run the portable runner with a PostgreSQL 17 binary directory and an existing private output root:

```powershell
./qa/linear-exit-rehearsal/run-portable.ps1 -PgBin '<absolute PG17 bin>' -Lane native-preinstall-backup -OutputRoot '<existing private output root>'
```

Add `-ObservedInputDirectory '<private observed capture directory>'` for the exact observed schema mode. This mode uses the four original captured catalog/definition/ownership files, verifies the published certificate, and uses the same ICU en-US locale as the observed reconstruction proof. It contains no hosted row data. Neither command contacts hosted Supabase.

## Later authorized capture invocation

Create a user-private JSON configuration file outside the repository containing the options above, with the encryption secret encoded as `encryptionKeyBase64`. Its filename may be passed on the command line; secret values must not be. The following adapter invocation needs no source edits and prints only the bounded success receipt or a fixed failure label:

```powershell
node -e "const fs=require('node:fs'),api=require('./scripts/linear-exit-native-preinstall-backup');const c=JSON.parse(fs.readFileSync(process.argv[1],'utf8'));c.encryptionKey=Buffer.from(c.encryptionKeyBase64,'base64');delete c.encryptionKeyBase64;api.capture(c).then(r=>console.log(JSON.stringify(r))).catch(()=>{console.error('BACKUP_FAILED; inspect private diagnostics');process.exitCode=1;});" '<absolute private config file>'
```

For the local restore check, use a separate private configuration with a literal loopback `connection`, `packageDirectory`, new `outputDirectory` and the same key record; change `api.capture(c)` to `api.restore(c)`. The returned scratch database name identifies the retained verification database. `diagnosticsDirectory`, if supplied, must be an existing private directory; tool errors can contain schema details and are never suitable for public logs. Do not execute this capture invocation until the owner authorizes the live read window and the source identity/catalog and coverage exclusions have been reviewed.

Earlier failed receipts are retained in the proof manifest. They exposed initial public-schema privilege handling, checkout byte drift, fixture locale mismatch, omitted publication/explicit default ACL metadata, and PostgreSQL inet-address formatting. The final tests retain the strict catalog comparison and do not convert these failures into live evidence.


## Opt-in online identity-sequence capture (2026-09-14)

The default remains strict before/after sequence equality. An explicitly selected `sequenceMode: "online-identity-v1"` permits concurrent sequence advancement without changing the public catalog or same-snapshot row checks. Its separate `native-preinstall-public-backup-online-identity-v1` manifest format is refused by older readers. The [online proof manifest](../independence/LINEAR_EXIT_NATIVE_ONLINE_SEQUENCE_PG17_20260914.json) records the updated source pins; the September 13 strict-mode receipts above remain historical evidence for their exact bytes.

The helper reads the native archive's exact `SEQUENCE SET` table-of-contents entries and parses their `setval` states without executing the extracted SQL. It requires complete unique coverage, one proven public identity-column owner per public sequence, no incoming catalog dependencies, matching sequence/column integer types, increment one, cache one, no cycling, and supported integer bounds. Empty-table maxima are represented explicitly as JSON null. Every archived next value must exceed its identity consumer's maximum in the same exported row snapshot and remain within the observed before/after sequence interval. Restore independently re-extracts archive states, verifies the stored bounds, restores the exact archived states, and rechecks the actual restored consumer metadata and maxima.

This proves safety for the identified catalog consumers, not discovery of arbitrary dynamic PL/pgSQL consumers. The manifest therefore retains `dynamic_consumers_proven: false`. Sequence state remains nontransactional; this is not an assertion that every sequence was captured at the same instant or that source writes were frozen. Unknown/unowned/nonidentity consumers, incoming defaults, cycling/caching/nonunit increments, unsafe maxima, exhausted bounds and out-of-interval states refuse. A strict-mode source-change diagnostic records only changed section names and sequence names in the private diagnostics directory.

Final online-mode evidence: generic PostgreSQL receipt `b0ed02b809164e1aa5ee12d7b527421e` passed 20 checks, including the retained strict controls and actual concurrent inserts; observed-schema receipt `ee05e3f1312b4eb1aef2eb6f6d0f100a` passed eight checks for the exact 67-table schema with 14 identity sequences. Both servers stopped. Parser/validator controls are distinguished from actual database controls in the new proof manifest. No live capture result is asserted by these isolated receipts.
