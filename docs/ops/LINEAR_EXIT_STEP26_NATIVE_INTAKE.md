# Step 26/27 — native intake and closure of its legacy fallback

This is a **design and acceptance plan only**. It authorizes no database access, flag change, deployment, workflow edit, or merge. Source statements are against current `main`; live measurements cited from the earlier session are not fresh verification by this document.

## Current source boundary

`native_intake_epochs` makes native intake durable, but it is not a complete legacy-exit closure.

| Path | Current behaviour | Effect of `linear_outbound_enabled: off` |
|---|---|---|
| Native `production-write` intake, including an ordinary real-client batch that straddles an epoch change | A pre-existing batch receipt preserves request identity and can retain an older empty epoch. For normal real-client, non-parity work, `production-write` schedules a drain only when `outboundLiveForDrain()` reads `live`; `linear-outbound` selects no normal real rows in `off` mode. TEST and legacy-parity exceptions retain their explicit behavior. | Stops the normal drain. It does not alter the stored request identity or reroute unfinished work. |
| Direct browser legacy submission | `_submitLinearFormRoutedOnce` can call `_submitLinearFormLegacy`, which posts to the legacy webhook directly. It bypasses `production-write`, the outbox, and the outbound flag. | No effect. |

The reported **“15 cards reached Linear”** is an earlier-session measurement, not reproduced or freshly verified here. That session's five checks did not reproduce it, but cannot prove the direct webhook path absent or detect it through an empty-epoch outbox query. Preserve the discrepancy as an open historical fact; fixing confirmed paths does not require a separate historical-audit investigation first.

## Gate 0 — read-only pre-cutoff disposition

Before final outbound cutoff, Storage records read-only checks for unfinished legacy batches/receipts **that are visible to the server**: each stable request/receipt identity, terminal or non-terminal state, and explicit disposition. A disposition is recovery on its existing identity, an owner-approved hold, or another documented recovery procedure.

**Server-visible and browser-held are different populations.** The legacy browser path writes its receipt to `localStorage` (`LINEAR_RECEIPTS_KEY`) *before* the webhook request starts. A browser interrupted before that request completes can hold a pending receipt that never reached any table Storage can read. A database inventory therefore proves disposition only for server-visible identities; it cannot establish that no browser-held receipt exists. Browser-held receipts are covered instead by the first browser exit below: on next open, the browser must show the saved receipt and its identity as a visible hold. **A visible hold alone does not dispose of the receipt.** Each browser-held receipt must reach either terminal recovery on its original identity or an explicit, approved disposition recorded against that identity. It is never re-issued under a new identity.

**Two separate questions, never merged.** *Recovery*: have the browser-held receipts that were **reported** been recovered or disposed of on their original identities? *Unreachability*: can an **old browser**, one that never loaded the new router, still create a **new** legacy submission? Answering recovery says nothing about unreachability. Reported receipts come only from browsers that someone opened and reported on. They **do not represent every browser**, and no count of them proves that no other browser holds or can create one. A browser-side hold only protects browsers running the new code; an old tab or a cached page still runs the old code and can post directly to the legacy form webhooks (`VIDEO_FORM_WEBHOOK` / `GRAPHIC_FORM_WEBHOOK`). So unreachability can only be answered by **enforcement at the receiving endpoint**, for both legacy webhooks. Record the two populations separately; do not report the server inventory as covering both.

Do not impose a batch age limit as a prerequisite and do not silently reroute an interrupted submission across identities or epochs. Root-history pinning prevents partial multi-item requests from splitting; any later change is optional, separate work.

## Confirmed browser exits to close

All four direct legacy-path exits require an identity-preserving, visible browser hold rather than a fallback POST.

| Exit | Required visible hold and recovery |
|---|---|
| Saved legacy receipt | State that the submission predates cutoff and show the receipt/request identity. Recover on that identity; never auto-convert to native. |
| `localStorage` read throws | State that saved submission recovery cannot be read. Do not choose legacy; preserve the entered draft and give an owner-recovery path. |
| Routing helper missing | State that the browser is incomplete/outdated and cannot safely submit. Do not POST; reload/update is recovery. |
| Routing returns `false` | State that the client is not enrolled for native intake. Hold visibly; **never** auto-enroll and never submit through legacy. |

The native-pending receipt remains on its native recovery path. Holds must neither overwrite nor discard a durable receipt.

## Step 27 — acceptance before cutoff (checks 1–10)

These checks accept the replacement. **All of them must pass before the final outbound cutoff**, and none of them depends on the cutoff.

| # | Acceptance check | Measurement |
|---|---|---|
| 1 | Every unfinished **server-visible** legacy batch/receipt has an explicit pre-cutoff disposition. | Storage read-only inventory and recovery/hold record, keyed by existing identity. Reported as server-visible only (see Gate 0); it makes no claim about browser-held receipts (check 3 covers reported ones) or about new submissions from old browsers (check 4). |
| 2 | All four browser exits show their specified visible holds, including a **browser-held** saved legacy receipt that never reached the server. | Offline browser tests for saved receipt (including one with no server-side counterpart), throwing storage read, missing helper, and `false` routing; each confirms zero legacy webhook requests. |
| 3 | **Every reported browser-held legacy receipt is disposed of on its original identity, whoever reported it and however it was reported.** A visible hold (check 2) is necessary but does not pass this check. | Offline tests show that the saved-receipt hold leads to terminal recovery on the original request identity, with no new identity and no duplicate card, and that an unrecoverable receipt stays held until an approved disposition is recorded against that identity. Live: **every** reported receipt is recorded with its original identity and either a terminal recovery or an approved disposition. That covers receipts reported by staff, by **clients** and by **videographers**, through **any channel** (in the app, Slack, email, a message to the owner, or a screenshot), not only those surfaced by a staff browser. A receipt reported without its identity is recorded as unresolved until the identity is recovered from the reporter's browser, and it does not pass. This check covers **reported receipts only**; it makes no claim about browsers that were not reported, and it is not evidence for check 4. **Recovery stays available after closure:** a receipt discovered later, from any reporter or channel, is still recovered or disposed of on its original identity, never re-issued. |
| 4 | **Old browsers cannot create new legacy submissions, shown separately for each legacy endpoint.** This is required before the legacy route may be declared unreachable. | **Endpoint enforcement is required for both webhooks; there is no alternative.** For **each** legacy endpoint, the video form webhook (`video-form`) **and** the graphics form webhook (`graphic-form`): **verified enforcement at that endpoint**, meaning its own configuration shows it refuses new submissions, plus **a refusal test run separately for that endpoint**. Each test carries its own unique, pre-recorded correlation identifier. The refusal is read back from that endpoint's response and execution record, matched by that identifier, and **zero business mutations** are verified for that identifier: no deliverable, batch, card, calendar post, `mirror_outbox` row, notification intent, Linear issue, or Slack message. **Explicitly exempt: the correlated fallback/telemetry row written by `LOG_SUBMISSION_WEBHOOK`**, including its row in the submission log sheet. That row is the record the correlation depends on, so it is expected, not a violation; the earlier blanket ban on a submission-sheet row contradicted this check's own evidence requirement and is removed. What that row may not do is **create or queue business work downstream**: no card, deliverable, batch, calendar post, queue or outbox entry, notification, Linear issue or Slack message may follow from it, verified for the same identifier. **The complete old-browser sequence is exercised and verified, not the form post alone.** An old browser first fires a **separate, fire-and-forget telemetry request** to `LOG_SUBMISSION_WEBHOOK` (`log-linear-submission`) **before** it posts the form, carrying the client name, the mode, the prepared receipt keys and the webhook payload; only then does it post to the team's form endpoint. The test drives that whole sequence from an old-browser page and records, for the correlation identifier: the telemetry request and what it wrote, the form post, and the refusal. **Retained telemetry is permitted and must be correlated:** the telemetry row, the endpoint's refusal response and execution record, and a refusal log entry all carry the identifier and are the evidence that ties the test to its outcome. They are not business mutations. Any record that creates, changes or queues business work is. Because `log-linear-submission` is a separate endpoint that this check does not make refuse, its retention is stated explicitly: it keeps receiving telemetry from old browsers after the form endpoints refuse, and the check verifies that what it writes for a refused submission is telemetry only and creates no business work downstream. A refusal on one endpoint is never evidence for the other. **Each endpoint's evidence is bound to the workflow version that produced it:** record, at test time, that endpoint's serving workflow identity, its active version identifier and a hash of the refusal guard as deployed, read back from the automation platform, not from the repository. The refusal and the zero-side-effect evidence count only for that exact recorded version and guard. Elapsed time, a stale-browser bound, a browser hold, a reported-receipt count (check 3) or a quiet outbox is not evidence for this check. The tests are TEST-only and Storage-authorized when run; this plan runs none. Any change to the webhooks themselves is separate approved work. |

A retry of the same submission (resubmit after an interrupted response, and recovery after reload) is accepted on the **same** request identity with no duplicate card. Zero legacy webhook requests. The service-only drill in check 7 does not exercise this route and cannot substitute for it. **The evidence is bound to the exact served build, taken from the deployment and then checked against what is served:** (1) from GitHub Pages, read the **latest successful deployment**: its build identity, its status, its `created_at`, and the **commit SHA** it published (`/repos/{owner}/{repo}/pages/builds/latest`, or the matching deployment record). A build that is not successful is not evidence. ## Step 28 — closure after cutoff (check 11)

| # | Closure check | Measurement |
|---|---|---|
| 11 | Final ordinary-real-row outbound cutoff, performed through Storage **after** checks 1–10 have passed and every other final-cutoff dependency is accepted. | **Immediately before the flag change**, Storage re-reads, for **both** legacy endpoints (`video-form` and `graphic-form`), the serving workflow identity, its active version identifier and its refusal-guard hash, and compares them with the values bound to check 4's evidence. It also repeats check 8's binding, compared against **the identity that was actually tested**: re-read the latest successful Pages deployment (identity, status, `created_at`, commit SHA), and compare it and the published artifact with the deployment and the **captured executing-navigation hash** bound to check 8's evidence, by the comparison check 8 establishes. All three recorded values must match that tested identity. **Any mismatch blocks the cutoff**, as does evidence that cannot be obtained: no successful deployment, a deployment whose commit cannot be read, a served page that cannot be fetched or hashed, or a publishing mode that has changed so the established comparison no longer holds. The cutoff stays blocked until the browser acceptance journey (check 8) is re-run on the build actually served, with its executing navigation response captured and hashed again during that run, and the evidence re-bound to that capture. A fresh fetch of the page, without re-running the journey, does not satisfy this. **Any drift blocks the cutoff**: a changed version, a changed or missing guard, a different serving workflow, or a version that cannot be read. The cutoff stays blocked until that endpoint is revalidated with a fresh check 4 refusal test and zero-side-effect evidence bound to the new version. Storage also reruns the Gate 0 server-visible disposition inventory fresh (not reused from check 1). The cutoff proceeds only if **no unfinished server-visible identity is left without a disposition**; any gap stops it. Then: flag-control receipt and readback of `linear_outbound_enabled`, with TEST/parity behavior checked explicitly. |

**Order.** Checks 1–10 accept the browser/native-intake replacement before the cutoff. Its holds, recovery of reported receipts, endpoint enforcement at both legacy webhooks, native intake on both teams, a successful browser Submit and retry, and identity-preserving recovery are its own evidence. The replacement therefore does not depend on the cutoff it enables. The cutoff is gated on checks 1–10, **not on "Step 27" as a whole**, and check 11 records it.

Final cutoff is not full Linear independence. It remains gated on accepted identifier-mint, intake, Workload, urgent-assignee lookup, brief media, and card-materialization replacements, plus checks 1–10. Only then may Storage perform the flag-control procedure that stops ordinary real-client outbound drains. Record **full legacy-route closure only after that cutoff** (check 11), and declare the legacy route **unreachable only on check 4's evidence: verified enforcement at both legacy webhooks**, still matching the versions bound to it at the check 11 re-read. The cutoff stops outbound drains; it does not stop an old browser posting to the legacy form webhooks. TEST/parity exceptions remain explicit, and a quiet outbox epoch is not evidence against direct-webhook bypass. Browser-held legacy receipts are disposed of under check 3 (hold, then terminal recovery or approved disposition), not by the cutoff.
