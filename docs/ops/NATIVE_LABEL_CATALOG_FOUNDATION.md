## Why this cannot yet activate

`production_label_catalog_check_manifest` validates all declared pages, cursor chaining, terminal completeness, total count, unique canonical UUIDs and every label's full applicability metadata before filtering. A self-consistent page file does **not** prove that the provider returned the whole workspace. `source_sha256`, the workspace fingerprint, team mapping and capture timestamp are retained claims, not authenticated provider facts. A deliberately truncated file whose final cursor/count are rewritten can be internally valid; its completeness is still unverified.

The current gateway also retains applicable provider outbox intents on accepted label writes, with F27 authority/generation checks and optional draining. Swapping its GraphQL catalog read alone would not establish zero provider egress. This foundation creates no rival retirement epoch or alternate write receipt.

Accordingly, `production_label_catalog_activate` and `production_label_catalog_read_active` **always raise `label_catalog_activation_held`, including for the service role**. No activation table, flag, setting, bypass parameter or automatic promotion exists. Every successful staging/validation result explicitly says `native_activation_allowed:false`, `native_commit_allowed:false`, and `verification_state:structure_validated_only`. Read results separately say `structure_complete:true` and `provider_completeness_verified:false`. Service credentials cannot turn those into an active catalog without another reviewed source change.

## Catalog and ownership contract

The manifest has schema version 1, a capture UUID, source kind `linear_workspace_issue_labels`, original-source SHA-256, workspace fingerprint, UTC capture time, `include_archived:true`, distinct canonical VIDEO/GRAPHICS provider team UUID mappings, expected total count and 1–50 cursor-linked pages of up to 100 rows each (at most 5,000 labels / 5 MiB JSON text). Every label retains original UUID, name, color, description, `archivedAt`, `isGroup` and explicit `team:null` or team UUID. Unknown applicability is rejected; known foreign-team rows are stored intact and filtered only when projecting an eligible team catalog. No label is manufactured from a selected-label union or partial cache.

One version UUID identifies immutable JSONB contents. The database computes a separate `manifest_sha256` over PostgreSQL JSONB text; this is not the digest of original export bytes. Repeating the same version and contents returns the same staging receipt; changed contents conflict, including concurrent submissions. New versions append. UPDATE/DELETE/TRUNCATE are refused by triggers even in ordinary owner SQL. A privileged database owner can still alter DDL/disable triggers; authenticated private backups remain necessary. `staged_db_session` records the database session role, not a verified human or staff member.

`production_label_catalog_validate_selection` is a **validation-only service seam**, not an accepted mutation receipt. The future caller must supply the complete selected relation from the exact authenticated, locked deliverable and its server-resolved team. It must never pass browser-supplied selected metadata. The validator permits new active global/same-team labels. An already selected archived, foreign-team or absent-from-catalog UUID can be retained or removed, preserving historical identity and metadata; that does not make it newly selectable on another card. Current active metadata wins on the same eligible UUID. Returned IDs are canonical/sorted and do not redefine the existing write fingerprint.
