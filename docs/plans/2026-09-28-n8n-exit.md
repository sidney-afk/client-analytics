## The four builds

**PR 1a and 1b: Filming Plan Tabs (biggest).** New Supabase function `filming-plan-tabs`
that keeps the single-document `{ok, docId, tabs}` answer for `?doc=<id>` and adds a bulk
form: `?docs=<id1>,<id2>,...` returning `{ok, docs:{<id>:{ok, docId, tabs}}}` (each entry is exactly the single-doc response), so one bad or
unreadable doc marks only that client as unavailable, exactly as today. It uses a small cache table
(`filming_plan_tabs_cache`: doc id, tabs, fetched at) so a Kasper open costs zero
Google calls when a copy is under a few hours old, and one request serves all
docs. The browser stops adding a cache-buster and `_filmsFetchTabMonths` (called per client
row today, `321` lines 2462 to 2472) is fed from one bulk request, with a per-row result
identical to today's, so no client is shown as unavailable or overdue that was not before.
A test asserts the full per-document response shape (`ok`, `docId`, every tab's `tabId`,
`title` and `url`), not just months and titles, against the current single-doc path.
**Manual refresh:** the Refresh button (`_kasperLoadFilming(true)`, which today skips the
30-minute browser cache and adds a cache-buster) passes `refresh=1`, which makes the
function re-read those docs from Google and rewrite the cache, so a newly added tab shows
at once. Only the automatic open uses the cache. A test covers both.
**Open question for the owner (blocks PR 1a):** the n8n flow reads the Docs with
an n8n-held Google OAuth login. A Supabase function would use the existing Google
service account (already used by the thumbnail and profile functions), which can
read a Doc only if that Doc is shared with the service account. I cannot test
that from here. If it cannot read them, fallback: the function serves the cache
and one small scheduled job refreshes it (about 34 n8n runs a day instead of about
1,400). I will build the cache and function either way, and say which mode works.

**PR 2: Calendar.** Send every Calendar write, reorder and read to the Supabase
functions. The server-readable runtime flag stays as the kill switch (ROLLBACK.md rule
1), but its off state does NOT fall back to n8n: those n8n endpoints lack the Edge
Functions' principal and client authorization (F67, ROLLBACK.md), so routing a rollback
there would reopen a known anonymous write hole. So: a flag that has not loaded, failed to
load or is malformed sends the save to Supabase (today it goes to n8n, which is where the
stray runs come from); a flag read successfully that does not list the client means
"saving paused for this client": the save is refused with a visible message and kept in the
outbox, never sent to n8n. Removing a client from the flag reaches open tabs two ways: the existing
realtime subscription, and, because a suspended tab or dropped channel keeps its old list, a
fresh flag read (bounded to two seconds, reused for about five seconds so a burst of saves
costs one read) before each write. If that read fails or times out the write is NOT sent on the cached
list: it stays in the outbox and the read is retried (the same saving state the page
already shows), because this is a write guard, not something the UI hides, and the flag
lives in the same Supabase project the save goes to, so a failed read means the save was
likely to fail too. A test covers a tab whose channel
is disconnected and a tab whose flag read fails. The check lives in the browser; the two frozen functions are not
edited. A test flips the flag and asserts requests stop and the
message shows. A bad function is rolled back the F51 way (redeploy the captured source), not
by rerouting. The n8n upsert constants are used only to replay already-pinned repairs
(below) and are then deleted.
Saved repairs already pinned `webhook` (`source_gate.source_transport`) are NOT re-pointed:
their completion check (`_writeUiLegacySourceRows`) reads from the pinned source, so
switching only the writer would leave them stuck at "Saved, syncing". They keep honoring
their pinned writer and reader until they drain. Zero n8n calls does not prove the drain:
a gate lives in each person's own browser, and a browser not opened that week makes no
calls yet still holds one. So the n8n upsert and get workflows stay on until dormant gates
are resolved by code, not by counting traffic: a returning browser loads the new page, and
on load PR 2 migrates each pinned gate together with its verification source (re-verified
against Supabase first, moved only if a test proves it atomic), or resolves it terminally.
The owner decides the cutoff for browsers that never return (open question). **Decision needed:** the
client approve and request-changes buttons save through this same shared
`_calUpsertFetch`. For the 43 enrolled clients they already go to Supabase, so
behavior is identical, but the code path is shared. I will add a test that the
approve and request-changes requests are byte-identical before and after, and
will not edit their code beyond the shared URL choice. Tell me if you want them
carved out completely instead (then n8n stays as their fallback for now).

**PR 3: Caption Prompts.** The `caption_prompts` table already holds every prompt
the n8n Sheet holds (26 rows, one more than the n8n list; every shared row is
identical or newer in Supabase). Read the table first; drop the n8n base read as the
normal path and the n8n save fallback. Keep an error-only fallback so a failed table read
cannot make Generate send an empty prompt (which would use the generic default, not the
client's stored one): a last-known-good copy in the browser, then n8n only if that is
empty. `Caption Prompts - Get` is NOT switched off in this plan: a new browser with no
saved copy has nothing else to fall back to, so it stays as the reachable first-load
fallback (a few runs a day at most, since it is only called on that failure). Only
`Caption Prompts - Save` goes, with `settings_ef_clients` kept as the same visible
save-pause switch as Calendar and Samples (off pauses caption saves with a message, never
reroutes to n8n), both modes tested (ROLLBACK.md caption-prompts row). Retiring `Get` needs a durable server-side copy
of the prompts that survives a failed table read, which is a separate decision. No new
function, no migration.

**PR 4: Sample Review.** Same as Calendar for `sample-review-upsert` and `-reorder`:
same routing rule and kill switch (`sample_review_ef_clients`, off means paused, never n8n); new saves never reach n8n; pinned repairs are handled as in PR 2, including the migration on load. `sample-review-get`
stays as the read fallback until a tested replacement recovery read exists (a retry of
the Supabase read, or a second Supabase path), and `_writeUiLegacySourceRows` is given
an equivalent before it goes.

Every PR carries a test that the path makes zero requests to n8n (a browser test
with every `n8n.cloud` request recorded and asserted empty), plus the usual gates:
`npm run build:index`, the affected suites, the identity check, and the fully mocked
`prod-write-gateway-browser.js` for Calendar and Sample changes. PRs 1 to 4 change
which transport Calendar and Samples save and load through (and PR 1b moves the Filming endpoint that
`qa/sxr_courier_lib.js` stubs by name as `/webhook/filming-plan-tabs`, so that stub is
re-pointed to the new function in PR 1b), so per the test-robot
rule in AGENTS.md each also runs the affected `qa/probes/` and `qa/ef-writepath/`
probes on its branch before merge, and updates that harness in the same PR if the
road moves. A PR that leaves the nightly red is not finished.

**Frozen writers:** `calendar-upsert` and `sample-review-upsert` stay ungated
(AGENTS.md freeze). Nothing here re-gates or edits them.

## Migrations and deploys

- **PR 1 is split in two, because merging to `main` ships the browser at once while the
  migration and the deploy are manual and come after.** The deploy lane also only accepts
  a commit already on `main`, so the backend cannot be live before its own merge.
  - **PR 1a (backend only, browser unchanged):** the `filming-plan-tabs` function, the
    cache-table migration (written, not applied), the `deploy-single-function` allowlist
    entry, and function tests. Nothing the page does changes, so it is safe to merge
    first. Once merged I name the commit to deploy from; the owner (or Lighthouse) applies
    the migration and deploys, and the function is verified live with a read-only call.
    The deploy is dispatched from
    `https://github.com/sidney-afk/client-analytics/actions/workflows/deploy-single-function.yml`
    (Run workflow, function `filming-plan-tabs`, commit = the SHA I name).
  - **PR 1b (browser cutover):** opened only after 1a is deployed and verified. It
    switches Kasper to the function, re-points the QA stub and adds the zero-n8n test.
    Until then the page keeps calling n8n, so there is no gap. 1b puts the cutover behind
    a server-readable runtime flag, `filming_plan_tabs_source` (`{"mode":"function"}` or
    `{"mode":"n8n"}`, default n8n until the owner flips it after 1a is verified), read live
    by open tabs. This route is read-only Doc tab titles, so pointing it back at n8n
    reopens no write or authorization hole. A test exercises both modes. The n8n workflow
    stays on for the whole life of the switch, and there is also an automatic n8n fallback
    on a function error. The owner retires the switch (and then the workflow) after a bake.
- PRs 2 to 4 are browser-only: no function deploy, no migration.
